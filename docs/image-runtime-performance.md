# 图片请求运行性能调整

当前实现整合 Aether 的异步网络等待、传输诊断及有界正文思路。保留现有上游协议、增量 SSE 解析、账号热池、评分、RT/AT 和内存调度索引；不实施紧凑账号索引重构。

## 图片网络等待

普通 `gpt-image-2` 的 `/v1/images/generations`、`/v1/images/edits` 非流式请求，以及 `async:true` 后台任务，共用一个专用 asyncio 图片运行时。外部同步请求仍在生成完成后返回图片。

- 通过 greenlet 在明确的等待边界接入 asyncio，复用原来的同步协议编排和切号规则，不做全局 monkey patch，也不复制一套旧协议。
- 初始化、凭证请求、上传、SSE、补查、下载使用 curl_cffi AsyncSession。每个账号尝试独享认证、Cookie、指纹和代理，并在该尝试内复用连接；不做跨账号会话共享。
- 网络等待及重试退避不占图片工作线程。选号/远程账号校验、PoW 等计算等待、图片合并与完整性校验、保存、日志和任务状态写入通过短工作线程执行；保留持久化确认。
- 账号写入的整个 `persisted` 上下文必须在同一个工作线程完成，不能让线程局部上下文跨越协程切换。
- `n>1` 且开启多图并行时，子图使用独立协程和账号，各自持有尝试上下文。关闭并行时保持逐张生成。
- `stream:true` 和 Codex 特殊图片模型继续走原有兼容执行器；这些路径仍复用共享传输线程池，不改其协议。

## 并发与取消

继续使用设置里的 `image_workers=W` 和 `image_queue_size=Q`。同步请求、异步任务和兼容执行器共用执行名额与 `W+Q` 接纳容量。队列满返回 429；调整 W/Q 后立即生效。W 是同时执行的请求任务数，单个请求的多图策略保留现有行为。

- 固定 4 个后台提交线程负责提交和启动；`image_dispatch_wait` 单独记录这一段时间。
- `image_admission_wait` 记录接纳后等待执行名额的时间，`image_queue_wait` 保留从提交到实际开始执行的总等待时间。阶段有重叠，不应直接相加。
- 取消只在共享的 100ms 检查器中处理，不为每条请求创建看门狗线程。静默 HTTP 连接会被撤销并释放；已提交的账号预留/写盘工作必须收尾并接回结果，避免遗留账号槽位。
- 请求总预算从原有计时起点连续消耗，排队、补查和换号不重新获得预算。排队期间过期的请求及时结束；后台任务在过期时仍写入可查询的失败终态。

## 超时及恢复

- `image_sse_timeout_secs` 默认 80 秒，从提交生成 HTTP 请求开始，包含等待响应头和接收 SSE；使用 libcurl 原生 TIMEOUT_MS。
- `image_poll_timeout_secs` 默认 10 秒，覆盖一次补查中的网络、退避和兜底查询。
- 硬流超时且已有对话 ID 时，先补查原对话的生成结果，不立即提交第二次生成。
- 无对话 ID，或原结果补查失败时，使用已有的 `image_poll_timeout_account_switch_retries` 控制切号次数，并与其他补查失败共用计数；0 表示不切号。账号尝试总次数限制仍有效。
- 仅剩不足 `min(20, image_sse_timeout_secs)` 秒时，不再为了流超时/补查失败提交新的生成请求，保留明确的结果未确定错误。此阈值只控制是否启动下一次尝试，不延长预算。
- 总预算耗尽与取消优先处理；安全审核拒绝不触发这种恢复，也不作为账号故障扣分。超时、补查和传输失败保持中性结算。
- 已拿到结果后的下载仍按下载超时和重试次数重试同一地址；重试耗尽后保留现有切号规则。

这种恢复有重复生成的可能：上游可能在本地超时后继续完成原任务。优先原对话补查和共享预算用于减少这种情况，不等同于上游幂等保证。

## SSE 诊断与正文限制

日志详情新增“生成流传输摘要”：响应头耗时、首段数据时间、最后数据时间、最长接收间隔、最后一段之后等待时间、字节数、段数、是否收到首段、EOF/主动结束/传输异常/超限。

摘要仅含时间、计数、结束类型和子图尝试序号，不记录原始 SSE、URL、认证和图片正文；沿用最多 160 个诊断步骤的固定空间。

图片下载最多 64MiB，SSE/元数据正文最多 16MiB，单条 SSE 行最多 1MiB。声明长度由 libcurl 检查，未知长度也在读取时按字节限制；超限会明确失败，不截断后当成成功。图片合并和原有完整性校验放在工作线程中完成。

## 事件循环监控

`phases.event_loop_lag` 监测 API 循环；`phases.image_io_loop_lag` 独立监测图片 I/O 循环。监控页分别显示最近延迟、近5分钟峰值、历史峰值和时间线。

| 字段 | 含义 |
| --- | --- |
| `last_at` | 最近一次采样检出时间，Unix 秒 |
| `max_at` | 进程历史最大延迟检出时间 |
| `recent_window_secs` | 近期窗口长度，固定 300 秒 |
| `recent_max_ms` | 最近 5 分钟最大延迟，毫秒 |
| `recent_max_at` | 近期峰值检出时间 |
| `recent_max_started_at` | 检出时间减去延迟，估计的停顿开始时间 |
| `timeline` | 近 5 分钟按 5 秒聚合的峰值、检出时间、最新延迟和样本数 |

API 循环每 0.5 秒、图片循环每 0.1 秒采样，分别最多保留 1200、3600 个样本，足以覆盖近5分钟窗口。聚合在统计锁外完成，不写数据库。时间线是采样观察值，不是操作系统调度追踪。

## 结果补查预算

- 首次等待不超过剩余预算的五分之一。
- 优先查询对话结果；首轮无结果再查询辅助任务，辅助查询不超过 1 秒或剩余预算的十分之一。
- 空结果沿用查询间隔；异常退避与二次确认给下一次查询预留至少 0.5 秒。
- 剩余预算无法容纳 Retry-After 时退出，不提前违反上游要求重试；外层兜底不重置补查和整个请求预算。

## 验证和复现

`test/test_image_async_runtime.py` 使用本机真实 HTTP 验证 200 并发、线程数量、取消、响应头/正文静默、预算、队列满、兼容路径共用名额、配置调整、Cookie/上下文隔离、正文上限、下载重试、文生图/图生图、URL/Base64、多图及后台任务终态。

纯 I/O 对照脚本：`scripts/benchmark_image_async_io.py`。两种模式分别在独立进程执行：

```powershell
.venv\Scripts\python.exe scripts/benchmark_image_async_io.py --mode legacy --output output/image_io_legacy.json
.venv\Scripts\python.exe scripts/benchmark_image_async_io.py --mode cooperative --output output/image_io_async.json
```

2026-10-31 本机单次样本：200 请求，每条 HTTP 正文保持 0.5 秒。

| 模式 | 冷运行 P95 | 热运行 P95 | 冷运行线程峰值 | 服务端最大同时在途 |
| --- | --- | --- | --- | --- |
| 原同步 I/O | 797.632ms | 650.888ms | 405 | 200 |
| 新协作异步 I/O | 796.464ms | 736.218ms | 7 | 200 |

两种模式的线程基线均为5。这个样本证明长网络等待的线程资源下降；热运行耗时没有优于原实现，不能据此宣称真实生图更快。独立图片循环观察到约97.718ms的累计延迟峰值，说明异步并不消除所有调度停顿。

测试不包含 TLS、WARP、真实上游、PoW、图片解码或持久日志，不是线上200张同时进入生成的证明。线上需要在相同配置和提示词分布下比较冷/热200并发的提交跨度、队列等待、两个事件循环峰值与恢复、PoW P95、CPU/内存、下载完整性和最终成功率。
