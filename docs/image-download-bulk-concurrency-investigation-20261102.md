# 发布后图片下载并发对照（2026-11-02）

## 结论

保留生产 **4 个下载进程 / 全局下载并发 64**。当前发布镜像上，单独把下载并发从 64 提高到 128，没有得到稳定且足够大的端到端下载收益，反而放大正文回传与调度等待、内存占用和事件循环延迟。本轮没有改产品源码、线上设置、Compose、镜像或 Git 分支，也没有部署。

本结果不支持把此前下载平台简单定性为服务器带宽不足，也不能证明网络在任何负载下都不会成为瓶颈。该测试是下载子链路，不是完整 500 并发生图。

## 测试方法

- 使用线上当前发布镜像 `sha256:acdb6ea107a8a0b483e9766c938858a1ef66be1b96179860fc312f6d1a1d5912`，在相同 Docker bridge 网络建立临时容器。
- 镜像内原生 transport、pool、worker；只挂载压测脚本，不挂载任何候选实现，不更改生产容器。
- 只从近期成功调用关联的 48 个账号读取各自最近至多两个对话及已有图片引用，并获取已有图片的有效下载地址。48 个账号均准备成功；未生成新图片、未更新账号 AT/RT 或状态。
- 48 个独立图片地址按固定次序循环至每轮 512 次，六轮总计 3072 次。每轮正文总量完全相同，为 1,438,899,388 bytes；总正文约 8.04 GiB。
- 全程 IPv4，固定 `chatgpt.com:443` 到 `104.18.32.47`；正常 TLS 校验，每个下载独立 Session 与认证上下文。相同来源不等于排除了 CDN 缓存及网络波动，不据此反推服务器套餐带宽。
- 4 个 worker 不变，只改变全局并发；顺序 `64 / 128 / 128 / 64 / 64 / 128`，轮间间隔 2 秒。每轮前检查生产没有在途、排队或下载任务。
- 每轮运行前创建并预热该轮下载池；正式吞吐计时不含 Python 导入/池预热。外部容器和网络采样则覆盖启动阶段，分析峰值时按正式计时窗口筛选。
- 单次下载超时 25 秒、请求诊断总预算 30 秒，不经过完整生图及产品上层重试切号；与生产的下载超时 15 秒不同。
- 正文只在内存中完整读取再释放，不落盘、不完整解码验图。逐请求断言 curl 接收字节、worker 发送字节、主进程消费字节相同；各请求存在 Content-Length 时校验相等，同一来源的每次、每轮长度均一致。未计算哈希，**不把长度一致等同于逐字节内容校验**。
- 0.25 秒采样宿主网卡、隔离容器 netns RX、cgroup CPU 和内存；实验循环另以 20ms 间隔采样 lag。采样并非连续硬件峰值观测。

## 分段分析

下面的分段 P95 按每种并发各 1536 个请求合并计算；不是先对三个轮次的 P95 求平均。

| 指标 | 64 | 128 |
| --- | ---: | ---: |
| 三轮吞吐中位数 MiB/s | 198.96 | 209.87 |
| 三轮含排队 P95 的中位数 秒 | 5.384 | 5.353 |
| 合并样本单次下载 P95 秒 | 1.811 | 2.152 |
| 合并样本等待测试名额 P95 秒 | 4.682 | 4.351 |
| curl 传输耗时 P95 毫秒 | 1770.17 | 1781.51 |
| curl 首字节 P95 毫秒 | 889.64 | 900.17 |
| curl 完成至 worker 正文读完/收尾 P95 毫秒 | 21.14 | 967.30 |
| worker curl 回调累计调度等待 P95 毫秒 | 181.43 | 602.89 |
| 主进程 IPC 请求至完成 P95 毫秒 | 1804.95 | 2145.15 |
| 主进程 RSS 最大值 MiB | 126.98 | 280.03 |
| worker RSS 采样最大值 MiB | 215.79 | 437.13 |
| 实验循环 lag 最大值 毫秒 | 32.84 | 87.58 |

- 吞吐中位数提升约 **5.5%**，三个 128 样本波动明显；含排队 P95 中位数只改善约 **0.6%**。只有三轮/参数，不做统计显著性或稳定收益承诺。
- 单次下载 P95 增加约 **18.8%**，内存明显增加；不能把等待名额缩短直接等同于整体完成更快。
- curl 传输 P95 基本相当，而 curl 完成之后的 worker 正文发送/消费及收尾时间差明显增长。这支持内部回传/调度背压被提高并发放大，但该时间差不是纯 IPC 线速，也不单独定位到某一个锁或函数。各阶段 P95 不能相加或相减还原某个请求。
- 主进程 CPU/墙钟约 0.77～0.83 核，主进程与四个 worker 的正式区间累计约 3.56～3.95 核。整机总 CPU 未满不意味着单进程链路没有瓶颈；也不能用平均值证明某一个核心一直饱和。
- 隔离容器正式下载窗口内，0.25 秒采样 RX 峰值分别约 415.48 / 461.54 MiB/s，CPU 采样峰值约 500.33% / 501.27%。这些是短时间网络/容器采样：RX 排除 lo，但仍包含协议开销，容器 CPU 包含回环 IPC 工作；它们不是有效正文持续吞吐，也不是物理带宽上限。外层 container_cpu_s 包含 Python 导入和 worker 预热，不与正式区间 CPU 核秒混用。
- 本轮重复使用已有图片，与完整生成期间的 CPU、线程、SSE、账号校验竞争不同；不能将下载 P95 套用到实际 500 并发生图。

## 决策

1. 当前不提高生产下载并发，保持 4/64；不为参数对照重启生产或重新发布相同代码。
2. 后续若继续做代码优化，先针对完整正文回传链路减少搬运/调度成本，候选必须保留完整正文、认证隔离、取消及预算、64MiB 上限，再以同源交替实验验证；不靠扩大缓冲、无限提高进程/并发掩盖背压。
3. 是否购买更多服务器带宽，本轮没有足够证据支持。已观察到当前源码内部路径对并发变化敏感，应先处理已被分段证据支持的部分。
