# 图片正文消费优化与发布验证（2026-11-02）

本轮减少图片正文从异步传输返回同步业务的重复切换与逐块预算计时器开销。已完成产品修改、针对性测试、本地 Compose 构建启动、Docker Hub 推送和线上部署。当前结果支持采用这项小改动，不能据此认定服务器带宽不足，也不能宣布完整 500 并发生图已经改善。

## 本轮改动

- `services/image_async_transport.py` 增加 `AsyncImageResponse.read_image_chunks()`：一次进入协作异步等待，在总预算内收集正文块列表。
- `services/openai_backend_api.py` 仅图片正文的异步响应调用新方法；同步兼容响应仍走原 `iter_content()`。
- 仍调用原 `_next()`，保留周期让出（256 KiB、64 块或 2 ms）、取消/预算检查、64 MiB 正文上限、诊断计数及 EOF 释放下载槽。
- 块列表仍由原工作线程合并和校验，未在事件循环合并大图片；不改变 SSE、元数据、账号认证隔离、下载重试及切号逻辑。
- 产品沿用原让出阈值；试验的 1 MiB 阈值没有一致额外收益，未采用。

本轮之前的工作树已有大量修改。部署前已把 15 个后端文件与旧镜像源码作换行归一化校验，0 个不匹配，证据为 `output/download_bulk_baseline_source_check_20261102.json`。本轮修改前的五个文件另存于 `output/_before_download_bulk/`（扁平文件名），没有将既有修改恢复到 Git HEAD。

## 归因与公平性修正

先在无外网容器中，用相同 IPC 管道传输内存正文。绕过整个适配层的参照较快，但它也绕过部分保护，仅用于定位，不能直接进入产品。单独移除 greenlet 的两轮结果不一致，不能认定它是唯一瓶颈。

第一版 bulk 实验消费方式不公平：原路径计数后立即释放块，候选保留整张正文。其内存与吞吐差异不能作为产品比较。后续统一让两边保留全部正文，与产品行为一致。

公平合成实验：4 进程、全局 128 并发、512 请求，每请求 3 MiB，共 1.5 GiB，隔离容器 `network=none`。

- 原路径两轮：249.96 / 276.68 MiB/s；含排队 P95：5.987 / 5.420 秒。
- 候选两轮：357.60 / 372.82 MiB/s；含排队 P95：4.176 / 4.013 秒。
- 两边主进程峰值内存均约 440～446 MiB，没有上述不公平实验所暗示的产品内存差距。

证据：`output/download_consumption_control_20261102.json`、`output/download_bulk_control_20261102.json`、`output/download_bulk_retained_control_20261102.json`。

## 发布前真实图片对照

复用此前已有图片，83 张可用图片循环组成每轮 512 次下载。并非创建 512 张新图。固定同一个 IPv4 peer、同样请求顺序、4 个下载进程、实验全局并发 128；不改生产的 64 并发。

最初一批真实对照的第三轮，出现一次 HTTP 200、EOF 但正文较短（1,260,818 字节，其他对照为 2,757,882 字节），且没有 Content-Length。该次 curl 已收字节、worker 读到字节、主进程读到字节三者相同，尚无证据指向 IPC 丢块；根因未确定。那批缺少 source_index，不能精确回溯对应来源，也不能称每轮图片正文均完整。证据保留于 `output/download_bulk_real_control_20261102.json`。

随后加强对照，逐次记录 source_index、字节数和 SHA256。四轮的 512 个 `(source_index, bytes, sha256)` 逐一相同，四轮总字节均为 1,410,323,184，且每请求 curl/worker/main 三层字节一致。SHA256 明显增加主进程 CPU，故这一批只用于正文一致性比较，不作为纯性能结果，也不等同于图片解码验图。证据：`output/download_bulk_verified_control_20261102.json`。

最后去掉哈希计算，保留三层字节一致性断言，再按“原、候选、候选、原”对照：

| 正文一次异步读取 | 128 | 207.39 | 6.069 | 2.237 | 5.990 | 30.120 | 215.76 |
| 正文一次异步读取 | 128 | 210.65 | 5.125 | 1.998 | 5.118 | 24.528 | 252.32 |

该计时批次每轮均为 512 个 HTTP 200、总字节相同、三层字节计数一致。网络依然有波动，合计 CPU 也不完全单调；可观察到候选的主进程 CPU 和含排队 P95 均更低，但不把四轮墙钟均值差当成固定收益。计时脚本中保留的空 digest 字段不作完整性证据。

## 清理、限制与下一步

所有本轮临时容器及 `/tmp/c2a-same-source-*` 目录均在 finally 清理；最终无探针容器残留、无调试器附加。真实图片只读入内存并释放，没有保存额外图片副本，没有完整解码验图，没有创建新图片。证据文件只保留计时、长度、哈希和安全诊断数据，不保存签名 URL 或账号令牌。Git 仍保留当前分支及全部工作树修改，本轮没有提交、合并或删除分支。

目前能确定代码的正文消费开销有优化空间，且候选缩短了该路径；不能据此把服务器带宽问题定性，也不能证明它不存在。真实测试的不同轮次仍有显著网络波动，短正文个例也尚未根因定位。

下一项应在同一下载源、同一批图片、同一发布镜像下比较全局 64 与 128，结合 NIC 吞吐、curl 接收速率、主进程 CPU 及队列长度决定是否提高生产下载并发。只有收益可重复再调整生产值。完整 500 并发生图的成功率和总耗时需另测，不能拿上述下载子链路结果替代。
