# 动态账号热池与按需刷新实现方案

分支：`feat/dynamic-account-hot-pool`。本文件记录最终实现规则与本地验收结果。当前实现已完成本地测试，尚未提交、推送或部署；生产成功率提升仍需部署后实测。

## 1. 目标与边界

提高首尝试成功率，避免全量刷新挤占生成路径；不能保证消除上游超时。继续使用现有内存选号索引，不实施暂缓的紧凑索引/LRU重构。本轮不操作生产、不自动推送或部署。保留现有AT/RT续期、轮换、并发保护和可靠保存逻辑。

## 2. 可用性确认

单一有效期X，最近可用性时间取账号信息校验成功、有效出图成功、上游明确安全审核拒绝三个时间的最大值。时间在X内跳过信息校验，否则先校验成功再生成；失败按切号预算换号。删除最大使用期限和过期缓存直接放行策略。

安全审核拒绝只证明实际发起该次上游请求的账号可用，不加减分、不算有效出图成功；本地敏感词和独立审核模型的拒绝不算。有效出图沿用图片下载完整性验证，不能仅凭HTTP200或URL记成功。认证失效、禁用、限流、额度不足、AT过期优先于历史成功；成功记录不能复活已失效账号。保留本地额度扣减与在途槽位保护。

## 3. 动态热池

基础账号数默认500，是健康热池目标，不是硬上限。热池内按健康状态、额度、槽位和评分分档轮转；容量不足时从冷池取得候选，必要校验成功、取得生成槽位后入热池。扩张仍受图片任务执行池控制，账号数不等于槽位数。

额度耗尽和明确凭据失效退出可用热池并触发补位。模糊超时采取有限退避，不能永久踢号或在系统故障时清空热池。闲置Y默认24小时，依据最后实际承接生成时间（从未承接则用入池时间）；后台刷新不算使用。在途账号不缩容，正常闲置缩容不低于基础目标。退出不删除账号、凭据或评分；不足基础目标时报告缺口。

## 4. 五条独立刷新通道

仅配置一个账号刷新并发C，分别应用到foreground、hot_fill、hot_maintenance、cold_maintenance、manual五条通道。C=100时每条各可执行100个不同账号，合计最多500个实际刷新。无后台减半、固定10/64/192上限、独立子查询并发或启动QPS配置。完成一个立即补一个，同一通道多个批次共享C。

同账号跨通道single-flight合并，跟随者等待同一个结果，不重复占执行槽位。身份需稳定且具备凭据/失效版本保护，不能因AT轮换启动重复校验或覆盖更新状态。等待有界、失败退避可见；维护用有界窗口，不将十万账号一次性转为Future。三个信息子查询的执行能力不能成为另一个隐藏小池瓶颈。

并发为单实例语义；本地锁不提供跨实例去重或分布式RT轮换保护。线程、文件描述符、端口、带宽、上游限流和机器资源仍是实际约束，不承诺加机器后线性扩展。

## 5. 到期维护与重启

热池维护间隔默认30分钟，冷池默认24小时，按账号持久化时间计算到期，不因重启重置倒计时。热池近期可用性确认可跳过无意义信息刷新；请求准入仍用X。冷池均匀错峰维护、分批执行并展示积压，不能整点扫描并提交全池任务。令牌续期/保活仍独立保留，信息刷新不保证会话永久保活。

## 6. 评分和切号

评分初始50、范围0至100；有效出图成功+1，明确账号相关失败可-5。安全拒绝中立；用户参数、取消、代理网络、存储等系统错误不扣账号分。模糊上游超时保守处理，连续失败才冷却。认证和额度硬状态优先于分数。

高分档优先、档内轮转，保留新账号和恢复账号试用机会，避免单账号热点。评分和热池身份随稳定账号保存，不随AT轮换丢失；单次尝试只结算一次。成功维护时，评分按距上次评分变更的整小时数向50恢复；不会自动解除认证无效状态。

校验和生成按单张图片共享账号总尝试预算。保留配置 `image_account_selection_max_attempts`，设置 N 表示最多使用 N 个不同账号（最多切 N−1 次）；`n>1` 时每张图片有自己的预算。轮询超时和文本回复分项上限仍保留，但都不能绕过总预算，避免重试层相乘。超时不代表上游已停止，不能盲目重复发起生成。

图片结果下载失败时，先按 `image_download_retries` 重试同一结果地址；下载重试仍失败后，可在同一账号总尝试预算内选择不同账号重新生成。每次切号仍受图片请求总时间预算限制；设置账号总尝试上限为 1 可禁用切号。下载传输失败只释放账号槽位，不因传输问题扣账号分。日志记录下载失败切号原因和尝试耗时。该兜底可能重复消耗生图额度；SSE/轮询超时的结果不确定路径仍不切号重新生成。

## 7. 设置与监控

基本设置集中为：可用性有效期X、基础热池数、闲置退出Y、热池维护间隔、冷池维护间隔、刷新并发C。失败退避/必要等待超时放折叠的高级设置；切号设置统一说明总预算和分项触发条件。

按用户要求不迁移旧配置，不做旧字段别名映射；缺少新字段时采用明确默认值。移除废弃UI、类型和消费路径，不重置鉴权、代理、存储等无关配置。

监控展示五通道limit/active/waiting、实际去重执行数、热池健康/空闲/缺口、扩缩原因和维护积压。账号信息可追溯校验/出图/安全拒绝时间及评分。结果指标区分有效出图、审核拒绝、失败、首尝试和切号成功，保留P50/P95。

## 10. 设置默认值与上线边界

| 设置 | 默认值 |
|---|---:|
| 可用性确认有效期 X | 900秒 |
| 每条通道的刷新并发 C | 50 |
| 基础热池账号数 | 500 |
| 闲置退出 Y | 86400秒（24小时） |
| 热池维护间隔 | 1800秒（30分钟） |
| 冷池维护间隔 | 86400秒（24小时） |
| 高级：失败退避基数 | 30秒 |
| 高级：校验/槽位等待上限 | 60秒 |

- 废弃最大使用期限、过期缓存放行、单独子查询线程数、手配后台队列、启动QPS及启动全量刷新策略；不迁移废弃配置。仍保留的同名配置字段按当前含义读取；升级后应在设置页重新检查保存，不改写无关鉴权/代理/存储配置。
- `refresh_account_interval_minute` 现在只控制独立AT/RT凭据维护检查间隔，界面已明确区分，不再触发全量信息刷新。
- 单通道最多保留2C个实际flight（含执行中），维护生产端另用C滑动窗口。队列容量自动推导，不再需要手配；前台等待有界，同账号等待超时不取消仍在执行的flight。
- 前台/手动合并到维护跳过查询的结果时，会重新要求真实校验，不能让较长维护间隔绕过前台X。此标记仅为内存类型，不增加调用方响应字段。
- 多次明确传输/上游5xx故障触发维护10秒保护，监控展示原因；不减少正常C、不阻塞前台，也不将整池账号踢出。维护失败弹窗保留最近200条脱敏记录，进程重启清零。
- 维护计划由持久化的账号确认/使用/入池时间重建；没有确认历史的冷账号按稳定身份错峰。账号信息与评分会随既有账号存储持久化。
- 首尝试/切号后出图率按**本进程、单张图片**统计，不含安全拒绝；原日期筛选结果区仍按保留日志统计，P50/P95含义不变。两种指标不是同一时间范围。
- 账号池列表增加热/冷身份、评分，并可悬停查看三种确认时间。
- 仍然全量加载账号，且新增到期索引会占用内存；本轮没有实现此前暂缓的紧凑索引/LRU方案。
- 同账号去重和并发闸门仍为单实例语义，不提供分布式凭据锁；C=1000不做64/192等软件截断，但线程、连接、内存、操作系统和上游限流仍限制实际能力。
- 未执行Docker构建/容器替换、线上压测、Git提交或推送。上线后再对真实图片有效性、首尝试成功率、切号率、校验等待、event_loop_lag及资源峰值验收。
