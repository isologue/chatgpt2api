# 完整元数据缓冲与 500 请求验证（2026-11-01，候选已撤销）

## 本次修改

`services/image_async_transport.py` 对原本非流式的元数据响应，直接通过 curl 正文回调写入有界 `BytesIO`。此前为了限制未知长度正文，这些请求也使用流模式，每个分片先进入 asyncio.Queue，再由协程逐片读取、计量和复制；现在在回调写入前执行同样的正文上限检查，减少分片队列和正文复制。

- 上限仍为解压后的 16 MiB，不依赖 Content-Length；超限用 `CURL_WRITEFUNC_ERROR` 停止 curl，再在协程边界抛出原有大小限制错误。
- 不能用普通短写或 return 0 终止：curl-cffi 会对短写告警，并报告完整写入长度；新增真实 HTTP 回归已覆盖这个问题。
- SSE、图片流式下载、账号认证/Cookie/Session 隔离和共享总预算保持原逻辑。
- 使用首次正文回调时间拆分 `http_headers` 与 `http_body`，以 `http_total` 和端到端计时判断整体效果，避免仅移动阶段边界制造提速。
- 下载并发 64、curl 回调时间片 2ms、SSE 80 秒、补查 10 秒、总预算 120 秒保持原配置。保留原账号内存调度索引。

本轮修改前快照：`output/metadata_sink_baseline_image_async_transport.py`。本轮工作区还包含前轮未提交修改，本记录只描述完整元数据缓冲这一项新增变化。

## 完整交替复测与撤销结论

不能仅采用第一轮的好结果。固定 1 秒发出 500 请求，后续结果如下；均完整采集 500 条应用计时和请求日志，无额外图片验图。

四轮空体 502 均为 0。最后一轮 504 包括 2 个 image_result_uncertain、2 个 image_timeout，发生过 2 次 curl28 下载尝试错误。前两轮延迟改善没有稳定复现，且相邻原版的首页回调 CPU 与候选几乎相同，不能将早先时段的改善全归功于这项改动。每次 down/up 也会重启代理，网络/上游状态并非固定，因此这组数据不足以证明全部退化由候选引起；同样不足以支持保留候选。

最后一轮有一条可以继续定位的内部证据：pow_solve P95 为 3498.162ms，其中实际进程计算 P95 为 5.33ms，进程池排队 P95 为 3415.58ms；相邻原版的计算/排队分别为 2.44ms / 17.60ms。首页解析、验证脚本与 PoW 共用进程池。首页解析排队 P95 从 262.97ms 升至 4515.39ms。独立分位数不能相加，但足以排除“PoW 阶段升高就是哈希难度升高”的误读；还需要区分解析工作堆积、跨进程传输和启动状态。
