# 图片并发的持久化优化与复测

2026-10-27：根据线上阶梯压测，优先处理集中完成后的图片索引与调用日志写锁竞争。账号的 PostgreSQL 存储和内存调度索引继续沿用现有架构。

## 写入与读取

- 图片元数据、日志索引使用各自独立的单写线程和复用的 SQLite 连接；WAL 与建表检查只在初始化时执行。账号数据库仍是 PostgreSQL。
- 每个写入器最多排队 1024 项，每批最多 128 项，聚合等待最多 4ms。这是内部持久化缓冲，与设置页的图片执行数、图片任务等待队列不同。
- 接收方必须等待整批事务成功确认；队列满时施加背压，不丢日志或元数据。异步 HTTP 路径等待 Future，不额外占用 AnyIO 接入线程。
- 保留 SQLite 的 FULL 同步级别。日志 JSONL 正文批量 flush/fsync 后才提交索引，事务失败撤回本批正文。正常关闭时等待在途任务并排空写入器。
- 日志列表、筛选和日汇总查询读取 WAL 已提交快照，正常写入期间不等待追加锁。进行中的批次会在提交后显示，分页仍以单次查询快照为准。
- 图片管理扫描按变更更新并比较旧值，保留扫描期间新增或更新的图片索引，避免旧快照全量覆盖。
- 同步和异步图片生成、编辑接口的返回数量不超过请求的 n。通用 Chat/Responses 的多图输出保持原语义。

请求体和响应体继续完整记录；阶段计时等元数据独立存放，不改动记录中的真实请求体或响应体。

## 队列观测

管理接口 GET /api/monitoring 新增 persistence.logs 与 persistence.image_index，包含：

| 字段 | 含义 |
| --- | --- |
| capacity | 等待队列最大项数，默认 1024 |
| queued / full | 等待项数 / 等待队列是否已满 |
| pending | 已接收但尚未确认的项数，包含当前正在写入的批次，可能大于 capacity |
| completed / failed | 已结束的项数（含失败）/ 其中失败项数 |
| batches | 已执行的事务批次数 |

队列按项数限制，并非按请求体字节数限制；大 Base64 请求仍会增加内存和磁盘使用。配置图片任务并发仍需考虑实际 CPU、磁盘和上游能力。

## 阶段计时

容器 INFO 日志新增 image_http_timing、image_task_timing 事件。同步图片调用的完整计时在 HTTP 最后一次发送之后记录；异步后台任务的完整计时在任务执行及调用日志确认之后记录。HTTP 计时止于 ASGI 发送完成，不能代替客户端实际收到响应的网络耗时。

调用日志详情包含 timing_id 与 phase_timings_ms，可用 timing_id 关联完整运行日志。详情中的阶段快照在调用日志入队前取得，因此本条日志自身的写入等待和后续 HTTP 发送耗时，以运行日志的最终事件为准。

| 阶段字段 | 含义 |
| --- | --- |
| request_dispatch_ms | 同步请求从进入图片 HTTP 中间件到提交执行器的耗时，含鉴权和解析等 |
| image_queue_wait_ms | 图片执行器排队时间 |
| account_lookup_ms | 选取可用账号时间，重试累计 |
| generation_work_ms | 各分图完整生成工作时间，包含下载和保存 |
| image_download_ms | 下载上游图片内容时间 |
| image_download_ttfb_ms | 从发起图片下载到收到上游响应头的时间，反映上游等待和线路首字节延迟 |
| image_download_body_ms | 收到响应头后读取完整图片正文的时间，反映正文传输阶段 |
| image_download_bytes / image_download_bytes_per_sec | 本次调用实际读取的图片字节数 / 按正文读取耗时计算的近似吞吐 |
| image_download_failures | 图片下载失败次数；不记录完整图片 URL |
| image_save_ms | 保存本地/WebDAV 图片及确认元数据索引的时间 |
| upstream_and_retry_ms | generation_work 扣除选号、下载和保存后的剩余时间，包含上游生成、轮询、重试及其余处理，并非纯网络时间 |
| log_persistence_ms | 调用日志构造、入队、等待正文与索引持久化确认的时间 |
| response_serialization_ms | 同步图片响应 JSON 编码及其线程调度等待 |
| response_send_ms | ASGI 响应发送累计时间 |
| http_total_ms / task_total_ms | HTTP / 异步后台任务完整耗时 |

并行 n>1 时，各分图阶段时间按工作量累加，可能超过请求墙钟时间；这些字段存在包含关系，不应简单相加。未执行的阶段不会出现。

完成通知按每个事件循环最多处理 64 项，剩余项通过下一轮调度继续恢复；这样可以避免大量图片同时完成时，单个回调长时间占用事件循环。`completion_delivery_ms` 记录每轮完成通知回调耗时。

## 2026-10-27 并发复测后的进一步优化

### 账号校验

选号仍使用内存调度索引；紧凑账号索引与按需详情缓存方案继续暂缓。校验由同账号共享 Future 合并，token 刷新改用精确账号锁，避免不同账号因散列锁碰撞相互阻塞。监控账号统计按增量维护，不再在账号每次修改后全量构建分页索引。

设置页“图片生成并发 → 账号校验与结果返回”可调整：

| 配置 | 默认值 | 作用 |
| --- | --- | --- |
| image_account_verification.cache_ttl_secs | 300 秒 | 成功校验后直接读取本地信息的有效期 |
| image_account_verification.max_stale_secs | 1800 秒 | 从成功校验开始计算的最大使用期限，至少为缓存有效期 |
| image_account_verification.background_refresh | true | 有效期过后、最大期限内先使用本地状态，同时尝试后台刷新 |
| image_account_verification.workers | 8 | 前后台共享的远程账号校验并发，独立于生图并发 |
| image_account_verification.queue_size | 128 | 后台等待容量，满时跳过刷新，不拒绝本次使用缓存的生图 |
| image_account_verification.starts_per_second | 8 | 每秒启动账号校验数；单次校验内部通常包含三个 HTTP 子查询 |
| image_account_verification.failure_backoff_secs | 30 秒 | 校验失败的初始退避，连续失败指数增加，最长 3600 秒 |
| image_account_verification.query_workers | 32 | 账号信息子查询线程数 |
| image_response_workers | 16 | 日志构造与图片响应 JSON 编码的独立线程数 |

后台最多接收 workers + queue_size 个校验任务，前台首次/硬过期校验通过图片请求原有的有界执行池接纳，前后台共享上述并发和启动速率限制。失败退避针对账号生效。普通安全审核拒绝、上游文字回复和连接超时不再无条件清空成功校验缓存；明确令牌失效时清空缓存，保留原刷新及切号行为。

成功校验时间 remote_verified_at 持久化，重启时只恢复未超过最大期限且时间合法的缓存。首次部署该版本、从未成功校验或轮换后的 token 仍要先完成校验，冷缓存突发仍可能等待；这些默认值不会保证冷启动的 1000 个请求立即进入上游。缓存减少预检频率，也不能保证上游不会限制或风控。

后台刷新提交结果前检查失效版本与 token 身份，避免旧结果覆盖认证异常/令牌轮换。刷新期间成功的本地出图数会从返回额度中保守扣除，手动禁用的账号保持禁用。

### 完成阶段与监控

日志构造与 JSON 编码使用有界独立执行器，监控使用单独的 2 线程、8 项容量执行器；它们不等待通用 AnyIO 线程。日志仍在正文和索引持久化后确认，取消发生于构造阶段时也完成写入。相同日期范围的监控采样合并在途调用并复用约 1 秒快照。

监控“已接纳未结束”包括排队、校验、上游、下载和日志确认；它不是上游正在绘图数。“上游调用中”表示正处于提交/事件消费/轮询流程，也不能证明上游已开始绘制。阶段表展示当前数、最近 256 个样本的 P95 和本进程累计完成次数，进程重启后重置。不同阶段存在包含关系，不应求和。

新增阶段 account_verification_queue / account_verification / account_verification_wait、upstream_generation、log_prepare、log_confirmation、log_write、image_completion_queue。image_completion_queue 包含容量等待及提交后真正的线程排队。持久化队列同时展示最近和最大排队耗时、实际写入耗时，供下一轮区分线程调度、队列积压与磁盘瓶颈。

本轮不提高 PostgreSQL 连接池上限：上一轮采样没有证据表明数据库连接池是主要瓶颈。线上分级复测须等待用户部署后进行。


## 2026-10-28：日志确认与选号热路径收缩

依据 `test_batch_output/loadtest-20261027/verification-retest/report.md` 中 500 档的日志确认 P95 约 76 秒、账号获取 P95 约 53 秒，以及事件循环停在运行日志 handler 锁的快照，本次仅修改本地实现，不调整线上参数。

- 运行日志由 4096 条有界队列、单后台线程输出，请求线程不再争用终端/容器输出锁。队列满时丢弃新运行诊断日志并计数，不阻塞事件循环；它与账号/调用日志的可靠持久化完全独立。
- 监控 API 增加 runtime_logging，展示 capacity/queued/pending/accepted/completed/dropped/failed。关闭服务时最多等待约 5 秒排空运行日志；异常慢的输出端仍可能使未完成的诊断日志在进程退出时丢失。
- BatchWriter 对同一批、同一事件循环的异步持久化确认只发送一次跨线程唤醒，再在所属事件循环中分发结果。同步写入 Future、异常传播、客户端取消后已接收日志继续写入、正文 fsync 后再提交 SQLite 索引的语义保持不变。
- 持久化监控增加 async_wakeups、last_ack_resume_ms/max_ack_resume_ms；请求计时增加 persistence_enqueue/persistence_queue/persistence_write/persistence_ack_resume，以区分入队、写线程排队、批次写入和提交后事件循环恢复。日志写线程另外增加 log_encode/log_append_lock_wait/log_index_sync/log_body_fsync/log_index_commit 阶段。指标有包含关系，不能求和。
- 校验缓存命中的正常选号路径合并为一次短账号锁快照，不再每次先获取令牌续期锁并重复 get_account。AT 剩余时间充足时，提前一天的续期留给已有后台维护；请求安全窗口取至少 5 分钟、且不短于图片轮询超时加 60 秒，窗口内仍同步续期，轮换后强制重新校验新 token。
- 定时维护中的 JWT 解析、RT 保活到期计算以及账号列表副本构造移出调度锁，锁内仅取稳定的账号引用/在途快照。继续使用现有内存调度索引，不引入数据库选号。
- 修复终态错误正则无法识别 refresh_token_reused 等下划线错误码的问题。已持久化的永久 RT 失败阻止自动续期，重启后仍生效；认证失败恢复的 force 也不会绕过，避免同一个已失效 RT 在不同请求中重复提交。仍有效的 AT、额度及账号可用状态保持不变。
- 替换 RT 会清除旧失败历史，旧 RT 的在途成功/失败结果不能覆盖并发导入的新凭证；瞬时网络/5xx 仍按原退避恢复。仅显式维护调用 refresh_access_token(..., force=True, retry_terminal=True) 可重新验证相同终态 RT，本次未新增 UI 开关。

定向测试涵盖慢输出、队列满载、失败后恢复、1000 条并发日志确认、多事件循环、取消不丢已接收写入、磁盘写入失败、RT 终态跨重启、替换 RT、普通错误退避、缓存单锁与后台扫描不持调度锁。上述均为本地回归，不代表实际上游 500/1000 生图吞吐已通过；待部署后再分档复测。


## 2026-10-28：500档复测后的批量索引优化

本轮依据 `test_batch_output/loadtest-20261028/report.md`：500并发日志确认P95约66秒、写入批次最大约59秒、监控8次12秒超时。仅据此不能断言磁盘或某把锁是唯一根因。本次不增大执行线程、校验并发或PostgreSQL连接池，不实施紧凑账号索引重构。

### 实际优化

- 日志摘要、索引行与统计值移到追加锁外准备。正常追加改为每100行一条多值SQL，单条最多700个绑定参数，兼容旧SQLite的999变量上限；同批每日图片计数与相同耗时桶先合并再更新。无需表结构迁移；旧日志重建及清理沿用原逐行恢复路径。
- 小JSONL正文合并写入，每块约1MiB；超过阈值的大Base64行直接写，不再拼接复制整批大正文。保留真实请求/响应内容、正文fsync先于索引commit、提交失败整批回滚及确认错误传播，禁止以丢日志换性能。
- 图片结果结算只按最终额度/状态更新一次内存候选索引，移除释放槽位后立即重复同步旧状态的操作；继续使用原内存选号索引，不在生图热路径查询数据库。
- RuntimePhases按阶段分锁，避免日志、账号、下载、监控的计数共用同一把锁；每阶段保留最多256个近期耗时及进程内最大值，仍不保存正文。
- 实测当前curl_cffi的Session.close只关curl，不关stream=True懒创建的线程池。backend关闭时显式shutdown已创建的流执行器（wait=False、不取消已提交任务），不在纯同步请求关闭时额外创建线程池。不会消除正在进行的SSE流所需线程，也不能据此承诺上游网络速度提升。

### 下一轮诊断

`/api/monitoring` 的 `persistence.logs` 新增 last_batch / slowest_batch：条数、字节数、成功状态、wall_ms、thread_cpu_ms、各子阶段耗时。只保留最近与最慢两份，不随请求增长。写入队列增加active_items、active_for_ms、last_batch_items、max_batch_items，可在IO未完成时查看当前批次。

新增账号阶段：account_selection_lock_wait、account_cache_lock_wait、account_read_lock_wait、account_slot_wait、account_token_inspection、account_token_refresh、account_foreground_verification；图片下载拆分image_download_http、image_download_collect。日志增加log_transaction_wait、log_body_append、log_index_update。原log_encode、log_index_sync、log_body_fsync、log_index_commit继续保留。

监控页“生图阶段与校验”下新增折叠的“查看锁等待与日志慢批次”，显示上述明细，无需增加刷新请求。P95只对应近期样本，max_ms及slowest_batch是本进程自启动以来的最大值，不是当前日期筛选值；不同阶段包含关系不变，不可相加。写线程CPU低但wall高仅提示等待/调度可能性，不能直接认定为磁盘慢。

### 验证与边界

- 本地1024条URL日志、128条一批、3次微基准：SQL语句从4152降到112，耗时中位数约56ms降至43ms。该基准不包含真实上游，不能换算成线上生图提速幅度。
- 回归覆盖：500条并发异步日志、正文保真、批量统计与耗时桶、筛选索引、整批写入失败回滚、正常读不等待未提交写入、线程池回收、独立阶段锁、结算只同步一次候选索引。
- 等用户部署线上后先复测200/500，只有监控及尾延迟恢复后再考虑1000；不自动修改线上配置或执行新的真实生图压力。

补充本地验证：305项定向回归通过，TypeScript独立检查通过，已执行 `docker compose -f docker-compose.warp.yml up -d --build` 完成本地构建部署。Linux新容器临时库500条并发日志约0.100秒完成，正文、统计和待确认状态一致。另有2个纯计算线程的人为GIL争用微基准（256条，3轮）中位数约96.207秒降至4.177秒，SQL1038次降至28次；这属于放大争用的本地实验，不是线上延迟预测。详细脚本、原始结果和修改前快照在 `test_batch_output/optimization-20261028/`。
## 2026-10-28 接入、账号临界区与完成通知优化

### 本轮改动

- 专用 Key 鉴权使用 SHA256 哈希内存索引，不再持管理锁等待数据库保存。last_used_at 在内存更新，由单后台线程按约60秒间隔合并保存，关闭时尝试排空；统计保存失败不拒绝有效请求。管理增删改仍同步持久化，后台写与管理写串行，不允许旧统计快照复活已删除/禁用/轮换密钥。进程异常退出可能丢失尚未刷盘的使用时间，这是统计精度与热路径解耦，不影响授权数据的同步提交。
- 图片入口鉴权不再无条件经过 AnyIO；未启用关键词/AI审核时跳过空过滤任务。启用规则时仍执行检查并将阻塞工作留在线程池，保留原拒绝和审核错误处理。
- 账号锁增加固定操作标签的 wait / hold / hold_cpu；指标统计在释放账号锁之后进行。槽位 Condition 等待不再混入持锁时间。候选索引同桶更新保留桶对象、原地轮转，避免无意义摘除重建；仍使用原全量账号内存调度，不引入生图热路径数据库查询。
- 账号持久化按原顺序在锁内入队，写线程启动移至 persisted 包装器锁外；持久化确认仍同步等待，失败传播。后台正常/限流账号筛选移至引用快照锁外。
- 图片执行和独立结果处理执行器使用按事件循环合并的完成通知，减少同时完成时的 self-pipe 唤醒。记录独立执行器 work、queue、resume 和 image_worker_resume；未启动任务可取消、已启动任务自然收尾，容量回调保持原语义。
- 每0.5秒采一次 event_loop_lag，最多保留256近期样本和进程最大值。不保存请求正文、账号或凭据。
- 实时监控和日期图片统计使用不同采集执行池、分别缓存和合并刷新。已有快照刷新超过约350ms可回退，返回 snapshot_state 的 collected_at / age_ms / stale / refreshing / refresh_failed，前端黄色提示。冷启动无历史快照仍等待真实数据，不返回伪造0；所有缓存项在途且达到上限时503，不无限新增采集。此改动不能保证同进程事件循环严重阻塞时仍秒回。
- 监控新增接入鉴权、过滤、事件循环延迟、选号持锁/CPU、结果处理排队/执行/恢复等指标。日期筛选不作用于进程运行指标，近期P95与进程最大值仍不可当作日期内逐请求计时。
