## 已能确认的结论

1. 服务器到同一图片域名、同一边缘地址，在本次测试条件下能提供明显超过生产约 40 MiB/s 的正文吞吐；不能据生产峰值判断为服务器带宽套餐已满。
2. 同一代码、同一数据、同一总下载并发 64，四个独立进程约 228～229 MiB/s，单进程约 56～74 MiB/s。代码侧单进程处理能力的瓶颈已实际复现。四进程下载 CPU 总量约 16～17 秒、墙钟约 5 秒，可利用约 3.2～3.4 个核；单进程 CPU/墙钟接近 1，符合单进程单循环处理受限。
3. 结合生产时已有数据停留在内核接收队列、底层回调等待，而 curl 完成后的正文读取收尾较快，应优先优化/隔离下载驱动、回调及正文读取与生图其他阶段的进程竞争。不能将某一段全部归因于 GIL，尚未把 GIL、Python 回调处理、CFFI 边界及事件循环公平调度各自成本分离。
4. 128 并发并不保证吞吐增加：扩大组的项目单进程 128 为 68 MiB/s，原生 curl 128 也下降至 61.8 MiB/s。测试没有隔离其源端/网络瞬时变化、TLS/进程启动成本和连接长尾的贡献，不能隐去此行、也不能声称已经找到稳定最佳并发。
5. 所有同源测试使用已有图片及重复地址，CDN 可能缓存；因此不能完全排除新图首次下载的回源延迟、CDN 限流或长时间链路波动。当前足以确定优先处理代码侧瓶颈，不足以承诺生产稳定 229 MiB/s、端到端提速三倍或精确服务器带宽上限。

## 下一步实施边界

优先原型化常驻的独立下载工作进程，先把下载与生成、账号元数据、运行日志的 Python 执行环境隔离，再以固定总下载并发对照。实验结果支持研究多进程，不能直接套用已否定的多线程/多个 I/O 循环线程方案。保持每个账号独立 Session、认证和 Cookie，保留总预算、下载槽位、取消、流量计数及错误恢复；必须测 IPC 和内存拷贝成本后再决定集成方式。
