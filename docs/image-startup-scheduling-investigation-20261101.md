# 图片启动阶段调度优化（2026-11-01）

## 当前结论与部署状态

本轮两个性能候选方案都没有达到保留标准，已经全部撤销。应用代码和监控 UI 恢复到进入本轮前的状态；本地 chatgpt2api:warp、线上容器及 Docker Hub 的 milodk/chatgpt2api:hot 均恢复为 2e32b8cdda30a65b7dec03bbf8ab6e4ad4964c83d2aa5e0d771c62cb2477e0ab。线上 Compose 内容未修改。

本轮只保留本实验记录、基准脚本及 output 下的数值证据和候选源码快照。没有把本地循环峰值下降描述成线上整体提速。以下候选实现及其测试结果是已撤销的实验，不是当前运行功能。

## 问题与范围

前一版本 500 请求波次在尚未出现下载正文流量时，curl 就绪队列已积压到 975 项，最长等待 4.456 秒。单次原生 socket 驱动最大 31.712ms，仍无法解释整个队列等待。见 image-internal-wait-investigation-20261101.md。

本轮继续保留账号私有连接、Cookie、认证、现有内存账号调度索引、下载并发 64、总预算及重试规则。没有新增并发配置或请求接纳限制。

## 分批准备请求候选方案（已撤销）

- 在 ImageCurlSession.pop_curl 前增加循环私有的准备队列，每轮最多唤醒 64 个准备请求。其它就绪网络事件、定时器和取消能够在两轮之间执行，不再一次唤醒数百个 curl 参数准备任务。64 是单轮唤醒数，在途请求数继续由现有图片任务配置控制；新增测试验证 500 个请求可以全部处于在途状态。
- 取消时从准备队列直接删除等待项，清空后取消调度回调。会话关闭先设置关闭标记，防止排队请求在 curl 清理的让出点重新创建 handle。队列调度不继承某个请求的 Context，任务仍保留自己的 Context；账号之间不共享 Curl、认证、Cookie 或连接状态。
- 网络回调批次恢复并保持原来的 2ms。定时器删除、就绪位合并、排队时暂停 socket 通知及最新读写兴趣恢复规则保持原行为。单次原生调用无法抢占，2ms 是批次让出预算，不是硬性单次执行上限。
- 以固定四类阶段统计回调排队：上游初始化、元数据、生成流、下载；另记录准备请求等待及队列峰值。监控页展示次数、平均等待、最长等待和最长等待起始时间。多个请求的等待会重叠，不能累加解释为单请求耗时或 CPU 用量。
- 每个循环仍只在本地更新固定枚举及数值，沿用 0.5 秒发布、5 分钟窗口、5 秒聚合，不保存账号、请求内容或地址。
