# 图片性能细分诊断

2026-10-31 增加少量固定枚举计时，用于定位 200 并发时首页预热、PoW 和图片 I/O 循环停顿。部署后自动生效，无需新增配置项，不调整生成协议、评分、切号或超时参数。

## 查看位置

日志管理 → 调用日志 → 详情 → **图片请求性能细分**。

- 慢同步片段：超过 50 毫秒才记录，每个阶段保留最慢一条及该阶段超过阈值的次数，显示北京时间、墙钟耗时和该片段 CPU 耗时。
- 分阶段计时：默认折叠，每个“阶段 × 性能项”只保存次数、累计毫秒、单次最大毫秒。
- 原有诊断时间线、请求体和响应体保持原行为。细分数据位于详情的 `diagnostics.performance` 与 `diagnostics.slow_slices`，不写入业务响应，不随日志列表返回。

新增计时不输出逐块 SSE 日志，不记录 URL、IP、函数参数、认证头、Cookie、Token、提示词和图片正文。阶段与性能项使用后端固定白名单；数据规模不随网络块数量、重试次数无限增长。正常请求同样有小型汇总，以免只采慢请求而无法对照。

## 字段含义

### HTTP

| 性能项 | 含义 |
| --- | --- |
| `http_headers` | 异步适配器启动请求至应用恢复并取得响应头的墙钟耗时；失败时记录等待至失败清理结束的耗时 |
| `http_body` | 取得响应头至响应读取、收尾完成的墙钟耗时 |
| `http_total` | 请求启动至读取收尾完成；流式响应直到关闭时才完成 |
| `curl_dns` | libcurl 记录的从连接起点至域名解析完成的累计秒数换算为毫秒 |
| `curl_connect` | libcurl 记录的从连接起点至 TCP 连接完成的累计时间 |
| `curl_tls` | libcurl 记录的从连接起点至 TLS 握手完成的累计时间；非 TLS/复用连接可能为 0 |
| `curl_first_byte` | libcurl 记录的从连接起点至收到首字节的累计时间 |

libcurl 数值在应用收到响应头时采集，使用复用连接、重定向、代理时，应按 libcurl 原有语义解释，不把累计值误认为每段独立耗时。它们也会受本机调度影响，不能单凭这些值断定是上游服务器处理慢。

`http_body` 包含流式消费、同步协议处理以及元数据正文合并的等待，不能当作纯网络传输时间。一次业务阶段可能发起多个 HTTP 请求，因此此处是聚合值。应结合各项的最大值、次数及工作线程计时判断。

### 工作线程

| 性能项 | 含义 |
| --- | --- |
| `offload_queue` | 协程发起阻塞工作至工作线程真正开始，包含提交分发和执行器排队 |
| `offload_work` | 工作线程开始至结束的墙钟耗时；如果其中等待 PoW 进程，也包含该等待 |
| `offload_resume` | 工作线程结束至图片协程恢复的等待，包含结果投递、事件循环排队和调度 |

这些指标按发起调用的业务阶段聚合，不记录原始函数名或参数。原先 `executor_submit_resume_ms` 仍保留历史含义，新字段用于细分归因。

### CPU 进程池

| 性能项 | 含义 |
| --- | --- |
| `cpu_submit` | 获取进程池与提交任务的耗时 |
| `cpu_queue` | 提交起点至子进程开始执行，包含提交、序列化、进程池排队 |
| `cpu_work` | 子进程函数执行的墙钟耗时 |
| `cpu_work_cpu` | 子进程函数执行期间实际消耗的 CPU 时间 |
| `cpu_return` | 子进程执行结束至父进程收到结果；同步路径含等待线程唤醒，协作路径在结果回调中记时 |
| `cpu_resume` | 仅协作路径：父进程结果已就绪至图片协程恢复，分离事件循环排队；历史记录没有此字段 |
| `cpu_fallback` | 保持原有容错逻辑，进程池失效后在父进程回退计算的耗时 |

同机进程使用 `perf_counter()` 的统一时基，跨进程只传输少量时间数值。计算成功才有完整子进程分解；异常和超时仍沿用原错误传播，此时父阶段/工作线程耗时可见，但不伪造已经取消或尚未结束的计算结果。`cpu_submit` 被 `cpu_queue` 包含，不能相加。

若 `cpu_work_cpu` 很低、`cpu_queue` 或 `cpu_return` 很高，优先查排队/IPC/父进程调度；若 `cpu_work` 和 `cpu_work_cpu` 都高，再关注计算量与 CPU。进程池外还可能有图片循环恢复等待；新协作路径对照 `cpu_resume`，旧线程包装路径对照 `offload_resume`。首页 HTML 解析、PoW 与验证脚本纯计算按其所属业务阶段分别记录，不把各阶段累计值当作单次 PoW 耗时。

### 同步执行片段

`sync_slice` / `sync_slice_cpu` 测量图片协议 greenlet 从获得执行权到主动让出或结束的每段同步执行的墙钟/线程 CPU 时间。等待网络、异步退避和等待工作线程期间不计入片段。

慢片段按让出点最内层阶段归因；若退出了业务阶段，则使用片段入口阶段。同一片段可能跨越多个业务阶段，不等于精确函数调用栈。这里只覆盖协议编排，未直接覆盖 libcurl/asyncio 内部回调；墙钟时间也可能包含 OS 抢占或其他线程持有 GIL 导致的等待。

超过阈值的片段也在监控 API 的 `phases.image_sync_slice_slow` 中按现有固定空间采样统计。它是慢片段分布，不能作为所有片段的 P95。

## 下一轮复测

保持相同生图配置，先跑一次 200 请求单波，并采集：

1. 客户端成功率、P50/P95、空体 502、图片完整性。
2. 每秒监控中的 API 与图片 I/O 循环时间线、Docker 资源采样。
3. 本轮调用日志详情里的 `diagnostics.performance`、`diagnostics.slow_slices` 与原有阶段时间线。
4. 以图片循环停顿的发生时间对齐慢片段；对比首页预热的应用响应头等待与 libcurl 首字节计时；对比 PoW 的进程排队、实际计算、结果回传和循环恢复。

累计值、父子阶段、CPU/墙钟时间存在包含关系，不能直接全部相加。单次最大值聚合也不等于完整原始样本：如要统计跨请求每次 PoW 计算的精确 P95，多次尝试请求需要另外说明聚合口径。若低开销计时仍不足以定位，再对下一轮前 30 秒做独立调用栈采样。

## 2026-10-31 后续优化

图片协作请求的首页 HTML 解析和验证脚本计算改走 CPU 进程池，原解析算法、会话预热及账号隔离不变。PoW 直接通过完成通知桥等待进程 Future，取消/总预算能中断等待；已运行的进程任务自然收尾。旧同步路径的 PoW 仍使用原进程池等待，其它元数据计算保留原线程内执行。

非常短的 requirements token 构造直接执行，去掉一次线程提交；这里不执行 PoW 求解。图片正文按调用方指定的块大小合并已到达的数据，合并上限 256KiB，不等待凑块，SSE 默认逐块消费保持不变。每消费 256KiB 已缓冲正文主动让出一次，让其他请求、取消和超时检查得到执行机会。原正文总上限、图片校验、下载重试、切号、评分与请求总预算继续生效。
