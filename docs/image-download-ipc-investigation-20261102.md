# 图片下载 IPC 与主进程消费调查（2026-11-02）

本轮只研究下载子进程到主进程的正文回传路径。结论：这条路径存在明显成本，但增大管道缓冲和合并帧写入没有足够的实际收益，不修改产品实现，不发布新镜像。生产保留 4 个下载子进程、全局下载并发 64。不能据此认定服务器物理带宽不足。

## 实验范围

真实下载复用已经生成的 83 张图，按固定顺序循环到每轮 512 个请求，每轮正文共 1,410,323,184 字节。没有新建生图任务，没有保存图片副本，没有额外解码验图。正式轮均为 HTTP 200、完整消费正文并匹配 Content-Length；这不是图片内容解码校验。

先准备 128 个候选地址，83 个可用，45 个返回 403 而被排除。地址准备阶段的失败不计入正式 512 请求。隔离下载预算为 25 秒，不经过产品上层下载重试、切号，不等同生产 15 秒超时下的最终成功率。

分段实验固定 IPv4 104.18.32.47，缓冲实验固定 IPv4 172.64.155.209；同批内固定，跨批 IP 不同，不把跨批吞吐差异归因于某个代码改动。每轮开始前确认生产 inflight 为 0。产品镜像不变，用临时容器只读挂载诊断副本。

## 真实下载分段对照

各轮均为 4 个下载进程，每轮 512 请求。

| 模式 | 全局并发 | 吞吐 MiB/s | 含名额排队 P95 秒 | 发送锁累计等待 P95 毫秒 | drain 累计等待 P95 毫秒 | Session 关闭 P95 毫秒 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 正文回传 | 64 | 191.03 | 5.575 | 224.57 | 36.77 | 10.05 |
| worker 读完后丢弃正文 | 64 | 220.49 | 4.587 | 0.006 | 0.013 | 11.33 |
| worker 读完后丢弃正文 | 128 | 257.31 | 3.764 | 0.005 | 0.014 | 13.15 |
| 正文回传 | 128 | 206.44 | 5.553 | 1044.72 | 50.81 | 9.02 |
| 正文回传参照 | 64 | 134.06 | 5.837 | 290.27 | 37.64 | 11.61 |

丢弃模式仍完整读取网络正文，但不把正文送到主进程；其吞吐是 worker 下载吞吐，不能当成可用于实际返回图片的性能结果。该对照减少的不仅有发送锁，也有正文 IPC、主进程缓冲和消费开销，所以不能单独归因于锁。

128 并发完整回传时：

- curl 传输耗时 P95 约 1675.61 毫秒。
- 同一请求的 curl 完成到 worker 正文读完时间差 P95 为 862.16 毫秒。按请求先计算时间差再取分位，不用两个 P95 相减。
- 最后一帧到主进程消费的 P95 为 3.19 毫秒。仅说明收尾消费较快，不能用它证明此前没有背压。
- summary 发送前到主进程收到的 P95 为 235.24 毫秒，包含发送锁等待、编码、发送及读取，不是纯粹的管道传输时间。
- 锁累计等待也包含背压和事件循环调度影响；不能把这些分段的 P95 直接相加得到单请求耗时。

64 并发末轮少量请求长尾至 9.279 秒，拉低整批墙钟吞吐；其含排队 P95 仍为 5.837 秒。不能仅看全批吞吐就宣布整体传输速度下降。

## 候选一：增大缓冲

4 进程、全局 128 并发；reader limit 从默认 64 KiB 改为 1 MiB，writer high watermark 候选为 1 MiB、low 为 256 KiB。

| 顺序 | 模式 | 吞吐 MiB/s | 单下载 P95 秒 | 含排队 P95 秒 | 主进程与 worker 合计 CPU 核秒 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | 默认 | 218.34 | 2.043 | 5.381 | 24.37 |
| 2 | 仅 reader | 119.12 | 2.011 | 5.112 | 24.07 |
| 3 | 仅 writer | 203.60 | 2.150 | 5.791 | 25.14 |
| 4 | reader 与 writer | 106.86 | 2.038 | 5.567 | 25.63 |
| 5 | 默认参照 | 179.78 | 2.055 | 5.642 | 25.05 |

第 2、4 轮有约 9 秒以上的少数下载长尾，不能凭墙钟吞吐认定缓冲扩大导致减速。仅 reader 的含排队 P95 略好，但只有一轮；writer 及组合并未一致改善，CPU 消耗没有明确下降。没有实际收益证据支持进入产品。

## 无外网的合成正文实验

为排除外网传输，在 network=none 的隔离容器中用内存源代替 curl。每请求 3 MiB，按 256 KiB 分帧；每轮 512 请求、合计 1.5 GiB。保留原 IPC 协议、主进程 WorkerResponse、协作运行时及正文消费路径。没有真实上游请求。

| 模式 | 全局并发 | 吞吐 MiB/s | 含排队 P95 秒 |
| --- | ---: | ---: | ---: |
| 默认 | 128 | 347.41 | 4.320 |
| 仅 reader | 128 | 418.64 | 3.559 |
| 仅 writer | 128 | 379.48 | 3.938 |
| reader 与 writer | 128 | 383.33 | 3.871 |
| 默认 | 64 | 308.05 | 4.858 |
| reader 与 writer | 64 | 355.80 | 4.200 |
| 默认参照 | 128 | 368.18 | 4.074 |

这只能说明该合成负载下的观察值，不能视为 IPC 的固定上限、真实下载吞吐或服务器带宽。合成正文不存在 TLS、网络碎片、真实 Cookie 及网络完成回调成本，不能把合成结果提升比例套用到生产。

主进程 process_time 接近各轮墙钟耗时，显示该合成消费路径有明显 CPU 成本。额外一轮 cProfile 仅用于查热点：socket recv、bytearray.extend、StreamReader.readexactly 都较显著；协作切换、预算/诊断和队列调度也有开销。剖析器本身降低吞吐，其数值不并入性能对照；greenlet 切换下累计时间不用于精确阶段归因。没有证据显示 Session 关闭是当前主要瓶颈。

## 候选二：每帧合成一次 write

临时 IPC 副本把帧头和正文拼接成一次 writer.write，锁、drain、协议、正文大小均不变。用无网络合成源做前后参照。

| 模式 | 全局并发 | 吞吐 MiB/s | 含排队 P95 秒 | 合计 CPU 核秒 |
| --- | ---: | ---: | ---: | ---: |
| 原实现 | 128 | 355.82 | 4.211 | 6.58 |
| 合并写入 | 128 | 325.75 | 4.604 | 7.60 |
| 原实现参照 | 128 | 339.92 | 4.404 | 6.78 |

候选没有领先，增加一次正文拼接还可能抵消减少写入次数的收益。不进入真实下载加压，不修改产品。

## 结论与下一步

1. 正文从 worker 回传并消费存在额外成本，现有数据不支持把下载并发提不上去全部归因于服务器带宽。
2. Session 关闭约 9～13 毫秒，远小于观察到的累计发送等待，优先级较低。
3. 增大管道缓冲、合并帧写入两个候选没有足够实际收益，均不采用。本轮完成的是定位和排除候选，没有可宣称的生产提速。
4. 如果继续研究，下一项应在同一无外网 fixture 下比较直接异步消费与现有协作消费，量化主进程记账/调度成本，再决定是否值得改正文接收方式。不能仅凭锁等待就移除锁或增加无界缓冲。
5. 任何后续传输改动必须保留帧完整性、64 MiB 正文上限、Cookie/认证隔离、总预算、取消确认及 worker 崩溃恢复；明确收益后才构建发布并复测完整生图。
