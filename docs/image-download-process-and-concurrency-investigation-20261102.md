# 下载进程数与全局并发联合对照（2026-11-02）

结论：本次没有得到足够证据把生产从 4 进程 / 全局并发 64 提高。8/128 快轮可达 199.26 MiB/s，但另一轮被少数长尾拖至 60.38 MiB/s；4/64 三轮为 147.96、176.48、195.43 MiB/s。8/128 含排队 P95 为 5.552、5.978s，和 4/64 的 5.648、8.358、6.084s 接近，没有稳定改善。16/256 未见收益，8/512 出现一次失败后停止加压。

## 测试方法

- 在线上同一服务器启动临时容器，使用相同生产镜像、相同 Docker 网络，固定同一下载源和 IPv4。镜像为 `sha256:9bdc1d3177c00fff2d7948c99296c39cc70733f1051660011b4f12f239b0e211`。
- 两批对照分别重新获取同一候选集合的已有图片下载地址。每批均 128 个候选，83 个解析成功、45 个 403 被排除；准备阶段的 403 不计为正式下载失败。
- 每轮使用 83 张既有图片循环组成 512 个请求；所有有效轮正文均为 1,410,323,184 字节，正文完整经下载子进程传回主进程消费并丢弃，没有落盘、图片解码或新生图。
- 每轮显式构造对应进程数的 `DownloadProcessPool`，预热后计时。全局下载并发不乘进程数。每轮前检查生产图片执行器无任务。
- 第一批计划 4/64、8/128、16/256、8/512、16/512、4/64。8/512 失败后停止，未执行 16/512 和该批末尾参照；随后只补跑 4/64、8/128、4/64，未再次提高并发。
- 实际峰值来自共享下载限流器 active 和所有 worker pending 合计，两者各轮均达配置值。这证明没有被原 64 名额限制；pending/active 不是所有 TCP 连接同一瞬间都在传输字节的证明。
- 本隔离脚本单次下载 timeout 为 25 秒，不走产品上层下载重试、切号和完整生成流程。生产下载超时仍为 15 秒、重试配置仍为 1。因此这里的失败不能直接换算成生产最终失败率。
- 成功条件为 HTTP 200、正文大于 1024 字节、存在 Content-Length 时正文长度相等。没有进行额外解码验图。

第 1～4 行为首批，第 5～7 行为补跑。共 3584 次正式下载，3583 次完整 HTTP 200、1 次失败。两次原生 curl 单请求预检及地址解析不计入这 3584 次。

“单下载 P95”从获得测试 Semaphore 名额开始计时；“含排队 P95”从该请求提交、等待名额开始，直到正文完整消费并关闭结束。全批墙钟吞吐受最慢请求影响，不能仅凭吞吐下降判断传输全程变慢。worker RSS 是各子进程采样 RSS 之和，含共享页重复计数；CPU 核秒是主进程和子进程累计消耗，均不等同 Docker CPU% 峰值或独占内存。

8/128 首轮单下载 max 20.593s，16/256 为 22.017s，而各自含排队 P95 为 5.552s、6.602s；这些少数尾部请求显著拖长整批时间。不能据此断言增加并发必然使吞吐降低到 60 MiB/s。补跑 8/128 达 199.26 MiB/s，也不能仅拿它对比一次较慢的 4/64 就宣布稳定提速。

8/512 实际准入峰值达到 512，511/512 成功，失败为 `DownloadWorkerError`、请求耗时约 25.004s。原脚本只汇总异常类型，没有保留该次底层错误码，故无法确证是网络超时、调度超时或其他 worker 内部原因。该轮正文少于固定基准，标记无效，不将脚本计算出的 53.51 MiB/s 用作完整成功吞吐对比。未重新加压 512 只为追错误；后续补跑脚本已增加错误码聚合。

## 结论与边界

1. 8/128 没有稳定拉开与 4/64 的差距，且下载子进程 RSS 从约 190～220 MiB 增至约 491～506 MiB。当前保留生产 4/64。
2. 16/256 单次样本消耗更多 CPU 和内存，未改善批次完成速度或 P95；8/512 已观察到失败，没有继续上调的依据。
3. 这次只测下载链路，包含子进程传回主进程，不包含完整生图的 SSE、账号调度、产品图片校验及写入。不能把 512 次下载误称为 512 并发生图。
4. 没有测得物理带宽上限，不能判定服务器带宽不足。更高并发未稳定增速，可能涉及主进程接收消费、调度、TLS/连接成本及网络长尾，本实验尚未将它们逐一隔离。
5. 如果后续继续优化，应先分清下载进程内传输结束、IPC 正文发送与主进程消费的分段耗时，再决定是否改变数据传递方式；当前无需仅为这组参数进行生产重启或镜像发布。

## 结束核验

生产仍为 4 个下载子进程、全局并发 64，SSE 80s、补查 10s、总预算 120s、下载 15s、重试 1。镜像 ID 和 Compose SHA256 均与测试前一致，Compose 未修改，容器未重启、无 OOM。执行器 inflight/queued 和下载 active/waiting 均为 0，worker TracerPid 为 0，没有残留测试容器；两批临时目录均在 finally 中确认删除。未保存图片或签名 URL 到结果文件。
