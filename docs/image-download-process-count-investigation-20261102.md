# 固定下载并发，提高下载进程数的对照（2026-11-02）

## 结论

固定全局下载并发 64，对比下载子进程 4、8、16，并以 4→8→16→8→4 顺序回测。当前没有看到增加进程数的稳定吞吐收益，生产继续使用 4 个下载子进程。8 进程最快一次与 4 进程快轮基本相当，16 进程未更快，进程内存和 CPU 时间有增加。

这次仅使用临时隔离容器，没有改变生产设置、镜像、Compose 或重启生产容器，没有生成新图、额外解码验图或保存图片副本。每次下载的正文完整经过现有子进程传回测试主进程，再由消费者读取并丢弃。

## 方法

- 使用当前生产镜像 ID：`sha256:9bdc1d3177c00fff2d7948c99296c39cc70733f1051660011b4f12f239b0e211`，同服务器、同 Docker 网络、固定同一 IPv4、同一批有效既有图片 URL。
- 从已有日志关联图片和账号，128 个候选中 83 个通过下载地址解析，45 个返回 403，未纳入正式测试。该准备阶段不是生成接口请求，403 不计为正式下载失败，也没有尝试绕过。
- 每轮同样 83 张图重复 4 次，共 332 请求、913,808,840 字节；每轮全局并发 64，不乘以进程数。4/8/16 进程满负载时大致分别分担 16/8/4 个下载。
- 每轮显式构建指定规模的 `DownloadProcessPool`，预热后开始计时。生产的 4 进程池不变，每轮开始前核对生产 inflight 为 0。
- 成功条件为 HTTP 200、正文非空且与存在的 Content-Length 一致，未做图片解码；启动前另用单请求检查可下载性。正式五轮均为 332/332 完整 HTTP 200，总 1660 次下载。
- 吞吐为完整正文有效字节数/该轮传输墙钟时间，包含正文传回主进程，不包含启动预热；延迟从获取并发名额后开始统计，不包含排队等待。
- worker RSS 为所有下载子进程 RSS 之和的采样峰值，含共享页重复计数，不等同于容器独占内存。每轮进程新建，避免前一轮分配器残留。CPU 时间为主进程加下载子进程消耗的累计核秒，不是容器 CPU% 峰值。

4 进程的两轮为 171.84、174.85 MiB/s；8 进程为 175.65、97.65 MiB/s，后一轮少量请求拖长整轮尾部（单下载 max 5.64s、P95 1.77s）；16 进程为 167.64 MiB/s。8 的一次慢轮不能独立证明进程数增加导致退化，但其快轮也未比 4 显著更快，暂不具备上调生产值的收益证据。16 只有一次样本，不能得出所有场景都更慢的结论。

RSS 采样上，4 进程约 207～209 MiB，8 进程约 324～342 MiB，16 进程约 610 MiB。8、16 的累计 CPU 核秒也更高；这属于当前测试成本，不等同于生产完整生图链路的占用预测。

## 解释与边界

提高下载进程数和提高下载并发是两个独立旋钮。增加进程在子进程自身事件循环、Python 执行或收包处理成为瓶颈时可能有效；全局并发保持 64，则同时占用的下载名额仍然是 64。此前原单进程至 4 进程的改善已经证明过软件限制，但不意味着进程数继续翻倍仍有同样收益。

现有分配策略为优先选择 pending 最少的下载进程；全部正文仍回到同一个主运行时读取。增加子进程不能直接提高主进程的接收、消费、调度能力，也不会增加服务器网络带宽。此次固定图片对照未出现稳定收益，进一步优化应测清正文消费者和 IPC 路径，再决定分摊子进程是否有意义。

本次隔离下载测试不包含 500 个完整生图任务的 SSE、解析、账号调度、产品图片校验和保存压力，因此不能排除“完整生图负载下 8 进程可能更好”。它也没有测出物理带宽上限。当前结论只支持“没有足够证据直接把生产提高到 8/16”，不宣称所有代码瓶颈已排除。

## 配置及结束核验

当前实现从容器环境变量 `CHATGPT2API_IMAGE_DOWNLOAD_PROCESSES` 读取进程数，默认 4，0 回退原单进程路径。代码位置：`services/image_async.py:157`。这是运行时启动配置，不是全局下载并发设置；要改变运行中进程数，需要使新环境变量在容器中生效并重新初始化运行时，单改宿主机 `.env` 不一定会传入容器。

测试结束临时容器和临时脚本目录已删除，未保存图片。最终核验生产仍为 4 个下载进程、全局下载并发 64，inflight/queued/下载 active/下载 waiting 均为 0；镜像和 Compose hash 一致，无 OOM、容器重启或残留 probe 容器。
