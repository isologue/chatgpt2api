## 本地可重复对照

服务端为独立进程HTTP/2 TLS服务，只传合成正文；每个请求独享Session、Cookie和连接，校验可信证书及完整正文。Docker以 `--network none` 隔离外网。当前版与修改前文件交替运行，每种大小各两轮、每轮500并发；正式对照先预热并在每轮前执行GC，避免把首次加载当成优化收益。

`512KiB` 正文复核结果：原版P95 2.176/2.081秒，修改版1.897/1.712秒，分别降低12.8%/17.7%；进程CPU原版2.219/2.134秒，修改版1.878/1.766秒。全部请求成功。`4KiB` 小响应没有稳定收益，不能宣称所有元数据请求都加速。

首次更大正文实验（含预热/GC波动）中，3MiB原版P95 14.257/13.129秒，修改版11.601/9.242秒；这只说明碎片多时计时器成本会放大，不代表真实首页大小或线上收益。

## 结论与剩余边界

- 本地合成HTTP/2复核支持保留减少计时器的小改；线上首页与最长回调排队数值有所下降，但不能宣称500并发整体提速。客户端P95变慢，应用中间件P95接近持平，图片循环延迟峰值反而更大。
- 两波各500条完整记录中，客户端平均耗时分别74.456/84.442秒，应用中间件平均计时分别68.214/65.197秒，平均差值从6.242增至19.245秒。该差值处于应用计时覆盖范围之外，现有数据不能区分客户端开销与进入ASGI之前的等待。不能简单拿两个P95相减作单个请求的阶段耗时。
- 旧版客户端发起时间分布跨度16.557秒，本版5.276秒，实际突发集中程度不同；下一轮需固定发起节奏，补齐客户端连接、发送、等响应头和读取的数值计时，再做对照，避免误判。
- 下载仍是明显的排队点：64名额、等待P95约22秒；下载较活跃期间，容器TCP接收队列积压峰值约61.76MB。数据已经进入内核但尚未消费的现象支持继续研究接收/回调处理；尚不能认定服务器带宽不足。观察到的单秒网络峰值也不能等同可持续带宽或业务下载吞吐。
- 不继续单纯提高下载并发，也不延长总预算掩盖问题。后续优先把客户端/接入等待测清，再用可重复本地HTTP/2负载分析碎片回调、TLS处理和调度积压，保留账号隔离。

当前保留本版小改作为后续观测版本，不把它标记为500并发性能问题已解决。最终健康核验：本地与线上镜像一致，线上running=true、restart_count=0、无OOM，inflight=0、queued=0，图片线程TracerPid=0；下载并发仍为64。此轮未新增Git提交或修改线上Compose。

## 后续计时校正（21:28 固定突发复测）

后续已确认原压测器每次创建 urllib opener 时，即使走本机 HTTP，也会在 Python 3.12 初始化 HTTPS 上下文并加载 CA。独立 500 并发合成对照中，该准备步骤 P95 达 7.621～16.367 秒。因此上文旧客户端耗时混入压测端开销；成功失败统计仍有效，延迟不能直接作为修正后工具的性能基线。

修正为显式 HTTPConnection 并固定 1 秒发出 500 请求后，495 成功、5 no_image_generated，无 504 或空体 502；客户端 P95 101.511 秒，中间件 P95 99.999 秒，客户端与中间件平均差额约 1.750 秒。发起节奏比旧轮更集中，不能把两轮延迟差直接归因业务代码。该轮保留服务镜像和配置，未重新部署。详细证据及剩余首页、回调和下载排队见 `docs/image-load-client-investigation-20261101.md`。
