# 图片下载进程隔离验证（2026-11-02）

目标：定位并改善下载并发增加后吞吐不升、名额排队的问题。只改变下载执行方式，保留原全局下载限流、账号隔离、TLS 校验、截止时间、重试与切号。

## 实现

- 图片 runtime 默认预热 4 个常驻下载子进程，各自执行 curl 网络收包；主进程继续管理账号、调度、正文校验和保存。
- loopback TCP 使用随机凭据认证和有界消息帧，将完整正文回传主进程，不把账号或图片写入临时文件。每次尝试使用独立 Session，保留 headers、cookies、代理和浏览器指纹。
- 全局下载并发仍为原配置 64，不乘以进程数。每次请求的绝对预算传入子进程。取消先等待网络终止确认，再释放名额；进程崩溃后失败请求走原重试路径，后续自动重建进程。
- `CHATGPT2API_IMAGE_DOWNLOAD_PROCESSES` 默认 4，设置为 0 可回退原单进程下载方式。生产 Compose 没有修改。
- `worker_total_ms` 为子进程该次下载总时间，`ipc_total_ms` 为主进程发起至终态确认的墙钟时间；两者差值不能当成精确 IPC 成本。

## 结论与保留边界

现在可以确认：原下载实现存在代码侧限制，分散到常驻进程后，同源对照和两轮实际生图都看到改善。现有证据不支持把原先的吞吐平台直接当成服务器带宽上限，也不足以证明任何并发下网络都不会成为瓶颈。

本轮保留下载并发 64。仍有约 258～260 个请求一度等待下载名额，因此不能宣称排队已解决。后续若继续优化，应在新架构下单独比较 64、96、128 的有效吞吐、正文 P95 和错误率，观察是否出现网络或 CPU 饱和；本轮没有修改线上这些设置或执行更高下载并发测试。

最后一次线上健康核验：镜像与发布 digest 一致，Compose hash 不变；inflight、queued、download active、download waiting 均为 0；4 个下载进程正常，TracerPid=0，无 OOM、无容器重启、无残留 probe 容器。本地构建、镜像推送和生产部署已完成。
