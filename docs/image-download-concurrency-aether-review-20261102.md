# 下载并发对照与 Aether 链路检查（2026-11-02）

## 结论

当前保留 **4 个下载子进程、全局下载并发 64**。在同一线上镜像下依次测试 96、128、64，每轮一次性提交 500 个生图请求；96、128 没有体现稳定的有效吞吐收益，128 明显拉长正文处理时间。三轮共 1500 请求，1466 成功，34 个失败全部为 `no_image_generated`；没有 504、空体 502 或最终下载失败。

本轮只通过设置接口受控改变 `image_download_concurrency`，每次都在空闲时切换并校验只有这一项变化，结束恢复 64。没有修改产品代码、重新构建或部署；生产仍为上一轮已部署的下载进程隔离版本。没有进行额外图片下载、解码验图或保存测试副本，产品原有图片校验继续保留。

## 网络还是代码

现有证据支持“仍存在正文消费、转发及调度成本”，不支持“服务器带宽不足是唯一瓶颈”。

| 单次下载诊断 P95 | 96 | 128 | 64 |
| --- | ---: | ---: | ---: |
| curl 报告的传输时间（秒） | 0.912 | 0.806 | 0.962 |
| curl 完成记录至 worker 收尾（秒） | 4.432 | 6.794 | 2.750 |
| worker 总时间（秒） | 4.999 | 7.227 | 3.249 |
| 主进程调用至终态确认（秒） | 5.997 | 8.314 | 4.026 |
| worker 回调最大排队时长（毫秒） | 11.494 | 14.203 | 12.473 |

curl 完成时间是在处理完成结果、释放 curl handle 前记录的。`completion_to_read_end_ms` 包含后续正文消费、IPC 发送、调度以及 Session 关闭；不是纯 IPC 耗时，也不是网速指标。这里比较的是每条诊断自身的时间差分布，没有把不同指标的 P95 相减。提高并发后 curl 传输时间没有同步变差，但完成后的收尾窗口明显拉长，说明继续提高并发会增加程序内部积压。

app 网络 RX 峰值是排除 loopback 后的容器网络采样，含生成链路其他流量；应用正文读取吞吐为 5 秒窗口，且受消费端调度影响，两者不能直接相减。短时 RX 峰值不等于持续可用带宽。本轮容器 RX error/drop 为 0，但有少量 TCP 重传；这既不能证明网络无问题，也不能证明链路已经饱和。容器 CPU 约 510%～555%，约相当于 5～6 个逻辑核，不能据此认定 32 核服务器整体 CPU 已满，仍可能是局部执行线程或调度路径限制。

上一轮固定同一 CDN IPv4、同一批既有图片、64 并发、正文完整传回主进程的交替对照中，原单进程为 80.33 / 77.52 MiB/s，4 个下载进程为 197.12 / 142.08 MiB/s。该结果证明旧实现存在软件限制，不能把此前 40～80 MiB/s 当成服务器带宽上限。它不能代表新生成图片的持续可用吞吐，也没有测出服务器物理带宽上限。

若后续继续改代码，优先对 worker 正文消费、IPC 发送和主进程接收分别采样，使用固定图片做受控比较；不再通过提高下载并发或延长超时猜测提速。本轮不为未经验证的推断修改产品传输逻辑。

## Aether 只读检查

检查了实际同步与流式执行入口至下载实现，未修改 Aether。相关文件与位置：

- `G:/Demo/Aether/apps/aether-gateway/src/execution_runtime/chatgpt_web_image.rs:1474`：`resolve_and_download_images`，1506 行开始按 URL 逐个 `await`，不是请求内多图并行下载。
- 同文件 `:1668`：`web_download_image`，1722 行把下载结果编码为 base64；当前项目 URL 返回路径不需要复制这一步。
- 同文件 `:1881`：同源带认证下载与外部公开存储下载分流。
- 同文件 `:1960`：`download_public_web_image`，1989 行在请求/重定向循环里重新创建 `reqwest::Client`，不是共享下载连接池。保留 DNS 校验、禁自动重定向和剩余总预算等约束。
- `G:/Demo/Aether/crates/aether-http/src/response_body.rs:59`：流式有界读取正文，同时检查声明长度和实际累计长度，并限制预分配容量，避免信任超大的 Content-Length。

值得认可的是原生异步正文读取、按剩余预算约束下载、有界正文累计。当前项目已具备相应异步块读取、正文上限和绝对预算保护；Rust 的执行成本优势不是复制几段客户端代码就能获得。没有发现值得直接移植、且能解决当前下载并发瓶颈的具体实现，因此不照搬其客户端创建、逐图下载或额外 base64 编码方式。
